# TaskChef Next sidebar demo

Call `open_taskchef_board` in Codex to open **TaskChef Next**. The sidebar keeps the TaskChef List and Board views, project/date/status filters, task cards, and detail view. This demo gets its data from local Codex session metadata. It does not read or modify the TaskChef dispatcher workspace. The web dashboard and dispatcher/report tools retain their current behavior.

On Node 22 or newer, the server first reads the 300 most recent chats from `~/.codex/state_5.sqlite` and their latest turn status from `~/.codex/thread_history_1.sqlite`. It uses read-only connections and indexed queries. It reads IDs, titles, timestamps, working directories, archive flags, and turn statuses. It does not read transcripts, `item_json`, tool output, or message bodies. A title is metadata but can contain user text; the sidebar displays it. The board shows the source and how many chats are outside the recent limit.

Opening the board queries the databases. While mounted, the sidebar requests a fresh snapshot every five seconds. Manual **Refresh** also queries immediately. The sidebar stops requesting updates when unmounted; whether hiding the sidebar unmounts it depends on the host. Reopening queries the current data when the sidebar mounts. Other board tools can also trigger reads.

If `node:sqlite` is unavailable or either database is missing or incompatible, the server uses rollout files. It inventories `~/.codex/sessions/**/*.jsonl` and `~/.codex/archived_sessions/**/*.jsonl`, sorts by file modification time, and parses the 300 most recent files. The server waits at least 30 seconds between ordinary file scans and at least ten minutes between full reparses; these are minimum intervals measured when a request arrives. Each incremental scan inventories and stats all rollout files to detect new, changed, moved, and removed files. It reparses only new or changed files within the 300 most recent. Manual **Refresh** checks immediately. The sidebar shows the file counts, coverage, and scan cadence.

The fallback scanner reads a bounded head and tail of each selected log. If the first metadata line crosses the usual 32 KiB head, it extends the head up to 1 MiB. It extracts session ID, timestamps, project directory, archive location, turn start/end events, and counts of visible user and assistant message records. It does not return request text, assistant text, tool outputs, or raw log records to the sidebar. Large logs can have unsampled content between the head and tail; the detail view shows the byte coverage. The sidebar shows a read/parse error count when selected files cannot be parsed. Both sources are read-only and make no model or GitHub calls.

A recent database `inProgress` turn or fallback `task_started` event can mark a chat as **Working**, but this is only an activity hint and can lag the desktop app. Database turn statuses `completed`, `failed`, and `interrupted` remain **Unresolved**. When a large fallback log has an unsampled middle and no turn event in its tail, recent file modification appears in the summary and `observed.recentFileActivity`. The chat remains **Unresolved** because the missing segment could contain a turn end. A turn ending does not prove that the user's task was completed. This demo does not claim semantic completion, review, or merge. An archive flag or location does not prove task completion. The **Open chat** action navigates to the recorded Codex thread. There are no status transition tools in the sidebar.

The UI is the bundled `ui://taskchef/task-board/v2` MCP resource. Build it with `npm run build:mcp-app`; run `npm run check:mcp-app` and the relevant tests before release. Reopen the sidebar after rebuilding the resource.
